## Findings — wave 1 (microbench, .backlog/lab/kbench/fp8bench.c, I=O=7168, median of 21)
F5. V1 (row-interleave R=4, keep LUT) = 1.04x only. So the 4-cache-line spread I blamed in E124 is
    NOT the main cost. Layout alone is nearly worthless.
F6. V2 (branch-free arithmetic e4m3 decode, ~60 ALU ops/16 weights) = 0.70x, SLOWER than the table.
    M3 has high L1 load throughput and the LUT is 1 KB / L1-resident, so table lookup is cheap.
    "Remove the LUT" is only a win if the replacement is nearly free.
F7. *** V3 WINS: 2.15x AND BIT-EXACT. 30.62 -> 65.87 GB/s. ***
    Two ingredients:
      (a) 16-row interleave so one column's 16 weights are exactly one vld1q_u8;
      (b) e4m3 -> f16 by REINTERPRET, not arithmetic:
            h = ((b & 0x80) << 8) | ((b & 0x7F) << 7)   =>  h_value = e4m3 / 256
          then vcvt_f32_f16. Exact for every non-NaN code incl. subnormals (e4m3 sub m*2^-9 lands on
          f16 sub m*2^-17; f16 min sub is 2^-24). The 2^8 is folded into the block scale (exact,
          power of two) so there is NO extra per-element multiply. NaN (0x7F/0xFF) gets an explicit
          compare+select because it would otherwise map to a finite f16.
F8. vfmaq_n_f32 is what makes V3 BIT-EXACT vs the scalar reference => clang IS contracting
    `acc += decode(w)*x` into FMLA at -O3. (E124 claimed mul+add was needed to match; that must be
    re-verified inside the engine build, whose flags differ from this harness.)
F9. Headroom left: 65.87 of ~104.7 GB/s = 63% of achievable.

## Findings — wave 2 (agents + prior art)
F10. REAL SHAPES (agent bg_ffed7cef, verified against models/deepseek-v4-flash/config.json AND the
     safetensors header). hidden=4096, heads=64, head_dim=512, q_lora_rank=1024, o_groups=8,
     o_lora_rank=1024.  Per layer per token, fp8 weight bytes:
       wq_b  I=1024  O=32768  x1  = 33,554,432
       wkv   I=4096  O=512    x1  =  2,097,152
       wo_a  I=4096  O=1024   x8  = 33,554,432
       wo_b  I=8192  O=4096   x1  = 33,554,432
       TOTAL 102,760,448 B = 98 MiB per layer per token; x43 layers = 4.42 GB/token.
     ALL have block_rows=128 on M3: v4_fp8_pack_rows8_inplace (:746-750) RETURNS 0 on non-AVX2, so
     packed_rows8=0 and fp8_view (:1818) sets 128. The AVX2 rows8 fast path is dead here BY
     CONSTRUCTION, not by accident.
F11. THE REPACK SEAM ALREADY EXISTS. v4_fp8_pack_rows8_inplace is called from the resident layer
     load (:800-809) and packs IN PLACE, setting spec->packed_rows8. On ARM it is simply a no-op.
     So "repack attention weights at load" is an existing, exercised code path -- I add the ARM arm
     of it rather than inventing a mechanism.
F12. *** E104 IS REFUTED BY MEASUREMENT. *** E104 (experiments_results.md:5305-5350) concluded
     "there is no bit-exact arm64 kernel that beats the current scalar code", from this dichotomy:
       - bit-exact => lane-per-row => only 4 weights decoded per step => arithmetic decode loses;
       - beat the LUT => decode 16 at once => must vectorise ACROSS COLUMNS in one row => order
         changes => not bit-exact.
     The second premise is FALSE. V3 decodes 16 weights per step that are 16 DIFFERENT OUTPUT ROWS
     AT THE SAME COLUMN (rows16 interleave). Each lane still owns one row and accumulates serially
     over ascending columns, so the reference order is preserved EXACTLY, while the decode is
     16-wide. Both properties at once.
     E104 only ever tried rows4 packing (its candidate B), which caps the decode at 4/step, and it
     ran SINGLE-THREADED whereas the real matmul_fp8 is `#pragma omp parallel for`.
     Measured refutation at the REAL shapes, median of 21, 16 threads, memcmp-verified bit-exact:
       wq_b 1024x32768 1.065 -> 0.510 ms  2.09x   bitexact
       wkv  4096x512   0.113 -> 0.070 ms  1.61x   bitexact
       wo_a 4096x1024  0.317 -> 0.139 ms  2.28x   bitexact
       wo_b 8192x4096  1.084 -> 0.508 ms  2.13x   bitexact
     Per layer 4.798 -> 2.200 ms; x43 = 206 -> 95 ms per token. The measured profile attributes
     194 ms to these phases, so the harness lands within 6% of the engine -- independent
     cross-validation of both numbers.
F13. PREDICTION: decode 599 -> ~487 ms/token => tok/s 1.67 -> ~2.05, +23%. To be proven at N>=5.
F14. CAVEAT TO CARRY INTO THE ENGINE: V3 uses vfmaq and is bit-exact against a scalar reference that
     clang CONTRACTED to FMLA at -O3 in MY harness. The engine's build flags differ; bit-exactness
     MUST be re-verified in-engine, and if the engine's scalar is not contracted the kernel must use
     vmul+vadd instead. Do not assume.
F15. BLAST RADIUS: c/quant.h is shared by colibri.c, inkling.c, kimi_k3.c, olmoe.c, deepseek_v4.c
     (E103). Therefore do NOT touch matmul_fp8. Put the kernel in coli_fp8_matvec_ref
     (deepseek_v4.c), exactly where the AVX2 path already lives -> DeepSeek-V4 only.
F16. wo_a is called 8x per layer on a 4 MB matrix and achieves only ~13 GB/s -- overhead-dominated,
     8 separate OpenMP parallel regions. Fusing those 8 into one region is a SEPARATE lever worth
     testing after the kernel lands.
F17. OPENMP (agent bg_664294c2). matmul_fp8's `#pragma omp parallel for` is entered
     3 + o_groups(8) + 1 = 12 times per layer per token in the attention path
     (wq_a :1881, wq_b :1928, wkv :1938, wo_a x8 :2074-2090, wo_b :2093).
     x43 layers x39 tokens = 20,124 region entries per generation.
F18. SECOND LEVER, FREE: deepseek_v4.c does NOT include c/omp_tune.h -- verified, the header is used
     only by colibri.c, kimi_k3.c, olmoe.c and a test. So V4 runs at libomp's default = 16 threads,
     which INCLUDES the 4 efficiency cores. omp_tune.h's own policy (:98-108) is to prefer
     hw.perflevel0.logicalcpu (P-cores only) because using hw.physicalcpu "slowed M1 Max by -4.2%
     decode". V4 never adopted it. Candidate: OMP_NUM_THREADS=12.
F19. LIBRARIAN (bg_d0c7ee6b): NO hardware FP8 on Apple M3/M4 (FEAT_FP8 = no, arm-cpusysregs dump),
     so no FCVT shortcut. vqtbl4q 4-way-split handles byte->byte maps but is worse than arithmetic
     for fp8->f32. llama.cpp ARM repack uses interleave widths 4 and 8. PyTorch/MLX use bit-twiddle
     arithmetic decode (which I measured LOSING as V2). The f16-REINTERPRET route that actually won
     (V3) was not surfaced by the literature search -- it came from the microbench.
     Apple's 300/400 GB/s figure is the SoC unified-memory spec; my measured CPU-side ceiling is
     ~105 GB/s, and that is the number that binds this kernel.
