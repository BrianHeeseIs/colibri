## 3. E132 hypothesis and why the prior rejection does not bind

`COLI_V4_HOT_PACK_UNLOCKED=1` (env, `c/deepseek_v4.c:8005`) allocates `policy->pack_mutexes` (`:8923`), which switches `lookup_hot` from `hot_pack_slot_locked` to `hot_prepare_slot` (`:8381`). `hot_prepare_slot` unlocks `state->mutex`, takes a per-slot pack mutex, relocks state, re-checks, unlocks state, runs `hot_pack_slot_compute` OUTSIDE the state mutex, then relocks. So it moves pack work out of the mutex the loader needs to publish a completed read.

Serena memory `deepseek_v4/dead_levers` rejects this lever as "-0.05%, ranges fully overlapping ... that contention does not exist in this configuration". The provenance of that rejection is `.backlog/lab/hotpack_ab_20260826-205025.log`: a p064 TTFT A/B, interleaved n=3, dated 2026-08-26, reporting `ttft=` only. It measured the PREFILL axis, four days before any decode instrument existed, at the one prompt length AGENTS.md warns is structurally incapable of exercising chunk- or group-conditioned behaviour. It is not evidence about decode.

E131 then DIRECTLY measured the contention it says does not exist. From A0 -> A2: d store_pack = +1062.950 ms, d store_hit_scan = +712.896 ms (also held under state->mutex), d store_lock = +510.586 ms, d wait_finish_complete_block = +269.050 ms.

Two defensible sensitivities, because pack cannot be cleanly separated from hit_scan as the causal held-time: on a pack-only basis dLock/dHeld = 0.4803 and dWait/dHeld = 0.2531; on a pack+hit_scan basis 0.2875 and 0.1515.

E132 removes ~694.6 ms of pack from the held region. Predicted: store_lock -333.6 ms (-71.5%) optimistic, -199.7 ms (-42.8%) conservative; wait_finish_complete_block -11.7% to -7.0%; tok/s +2.93% to +1.74%.

State the mechanism precisely: E132 does NOT remove the pack compute from the main thread's wall. The main thread still executes it. What E132 removes is the MUTEX EXCLUSION during that window, so the critical path stops locking out the loaders it will later block on.

Carry this honesty caveat: the trace prints `note=store_nested_is_nonadditive_due_to_worker_overlap`, so 697 ms must NOT be treated as a subtractable slice of decode_wall. The E131 co-movement is the evidence, not the raw stage total.

## 4. The credible cancelling term (why this is gated, not assumed)

`hot_prepare_slot` is invoked on EVERY lookup when pack_mutexes is allocated, including the `should_pack == 0` branch (`:8529`, `:8758`), and that crossing is load-bearing for correctness so it cannot be optimised away. That is 10062 extra unlock/lock/lock sequences per run. At the measured contended acquire cost of 46.3-46.8 us, a full-cost re-acquire is 10062 x 46.8 us = ~471 ms of NEW wait, which brackets or exceeds the predicted 200-334 ms saving.

Critically: `store_lock` has `calls=10062`, exactly one per lookup, so the timer wraps only the FIRST acquire. The added re-acquire is INVISIBLE in the primary gate and lands only in expert_forward_ms / decode_wall_ms. This is why the reversal guard below is mandatory: without it the probe could report a 60% store_lock win on a lever that is net slower.

## 5. Bit-exactness is NOT assumed

`hot_prepare_slot` (`:8389-8392`) carries `if (!should_pack || slot->references != 1 || policy->packed[slot_index])` which `hot_pack_slot_locked` (`:8364-8377`) does not. A slot with a concurrent outstanding lease is left UNPACKED under the unlocked path but PACKED under the locked path. Different rows16 coverage means a different kernel runs, which means different arithmetic. E97 already proved a rows16 coverage change can change tokens. The prior "bit-exact both ways" claim rests on the p064 TTFT log and is therefore not established for decode.

(`expert_forward` -4.64%), so it reaches the finish barrier sooner and therefore waits LONGER for a

wall time, and only the residue shows up as `decode_wall` -1.58% / tok/s +1.60%.

consistent with E130: `store_disk_read` is 16.7% of decode wall and the loader already hides 50.2%
