### The "+26% vs 6% coverage" contradiction is real, and it is in the BACKLOG's own framing
- backlog:9 "Ceiling if it delivered 2x on the phase: **+26% decode**"
- backlog:10 "only ~6% of decode expert calls reach the NEON path at all"
These cannot both bound the SAME work item. 2x on the PHASE requires the fix to reach ~100% of
expert calls. Fixing `neon_rows16_accumulate` alone touches 6% -> 6% x 50% = ~3% of the phase =
~1.25% of decode = BELOW the 5-13% noise floor. So P0-as-literally-written cannot deliver its own
stated ceiling. The backlog:63-65 already half-says this ("a faster NEON kernel must ALSO be made
reachable"), but the headline number does not carry the caveat.

### Dispatch, exactly (c/deepseek_v4.c)
:8974  rows16 NEON taken ONLY if gate/up/down all have block_rows==16
:8167  block_rows=16 set ONLY if policy->packed[...]  (i.e. pinned)
:8338  should_pack = hot_is_pinned(...)
:8690  default_pins = min(maximum_pins,16) of 256 experts/layer  => the ~6%
=> 94% of decode expert calls run SCALAR matmul_mxfp4 (c/quant.h:1440), which has NO aarch64 SIMD.

### The scalar path ALREADY hoists the scale; the NEON path does NOT
- quant.h:1456 accumulates g0..g3 UNSCALED within the group
- quant.h:1481 applies scale once:  a0+=g0*c0; a1+=g1*c1; a2+=g2*c2; a3+=g3*c3;
- NEON :14612 applies per element: sums[g]=vaddq(sums[g], vmulq(vmulq(x,values), scales[g]))
So the hand-written SIMD kernel is arithmetically HANDICAPPED relative to the scalar C one. That
alone explains why SIMD is only 1.03-1.14x faster than scalar (E126 head-to-head).

### NEW HYPOTHESIS (stronger; explains every recorded number) — LATENCY-BOUND, not bandwidth-bound
Evidence: both kernels sit at 16.6-18.9 GB/s against a ~105 GB/s measured host ceiling (17%), and
the fp8 kernel in the SAME engine reaches 65.9 GB/s. Not bandwidth-bound.
Both kernels keep exactly FOUR independent accumulator chains (scalar g0..g3, NEON sums[0..3]),
each serially dependent for the full 4096-column run.
This is the SAME defect that made the LM head slow: E126a took `head` 1399.6 -> 524.4 ms (2.7x)
purely by keeping 4 accumulator chains instead of 1 — latency-bound on a 4096-deep chain.
Predicts: SIMD ~= scalar (both 4 chains), both far below BW ceiling, pin coverage worthless
(converting between two equally latency-bound kernels) — which is exactly E123's flat result.
Predicted fix: widen ILP (multiple activation elements -> separate accumulator sets) AND hoist the
scale so the chain op is one FMA instead of mul-mul-add.

### llama.cpp reference idiom (librarian, head 0b5be7e4)
ggml/src/ggml-cpu/arch/arm/quants.c:749-807 `mxfp4_q8_0`: nibble LUT via vqtbl1q -> integer dot ->
apply block scale ONCE: `sumf += E8M0_half * fp16_d * vaddvq_s32(prod_1)`.
Universal idiom: decode 4-bit, accumulate WHOLE block, scale once. Fewer FP roundings, less MUL.
CAVEAT for us: llama.cpp quantizes the ACTIVATION to q8_0 so it can use vdotq_s32/vmmlaq_s32
integer dots. Our activation stays fp32 -> we cannot copy that directly; we use float FMA.
E8M0 -> float is free via exponent-field write: for x>=2, bits = (x-1)<<23 (ggml-impl.h:475-498).
Pitfalls: low nibble first; codes 8..15 negative; vqtbl1q zeroes out-of-range idx; e2m1 has no
NaN/Inf in element form (block scale carries 0xff=NaN, see coli_e8m0_decode :13503).

## Oracle verdict (bg_30cc2f8f) — my hypothesis PARTLY REFUTED, target confirmed

### Refutation I must carry forward
"Low GB/s does NOT prove add-latency." ANY compute- or permute-bound kernel shows low memory BW.
My "4 accumulator chains" story is TOO NARROW. Verdict: **backend-execution limited**, not bandwidth
limited. The cold scalar path is plausibly recurrence-limited, but the rows16 path has an EQUALLY
strong TBL/permute bottleneck that I had not costed:
  inner loop per call = 1x vqtbl1q + FOUR vqtbl4q.
  Firestorm-class proxy: TBL 1-reg = 2c / 0.25 cyc; TBL 4-reg = 4c / 0.75 cyc / **3 uops**.
  Permute uop pressure ALONE can pin the kernel in the same 25-33% band.
So "SIMD ~= scalar" is fully consistent with dequant/permute backend cost, NOT uniquely with
accumulator latency. Both stories predict the same observable. I cannot pick between them from the
recorded data.

### Saturation arithmetic (public Firestorm-class proxy, NOT claimed-exact M3)
FADD v4s latency 3c; FMUL/FMLA v4s latency 4c; SIMD/FP issue width 4 uops/cyc.
=> saturation needs ~12 independent FADD chains or ~16 independent FMLA chains.
Current 4 chains feeds ~33% (FADD) / ~25% (FMLA) of peak. Consistent with the 17%-of-BW observation
but NOT proof of it.
TRAP Oracle flagged: `float32x4_t sums[4]` is FOUR dependent vector chains, not 16. Lanes are not
independent chains. (I had this right, but it is worth pinning.)

### THE DISCRIMINATOR (do this before writing any kernel)
"Keep the decode/TBL path UNCHANGED and only increase the number of independent accumulators.
 If speed scales -> recurrence is primary. If flat -> TBL4/uop pressure is primary."
Cheap, decisive, runs in kbench with no model load. This is the valid probe V2 should have been.

### PARITY-PRESERVING ILP EXISTS (big — changes the risk profile)
Widen across INDEPENDENT FINAL SUMS (more output rows / row-blocks in flight), keep ONE serial
accumulator per final sum, keep the SAME term order, and allow NO FMA contraction.
What BREAKS parity: splitting a single sum into partial sums reduced later, reassociation, FMA.
=> Processing 4-8 OUTPUT ROWS concurrently gives ILP with per-row term order untouched.

### DEFERRING THE BLOCK SCALE MAY BE BIT-EXACT, NOT APPROXIMATE
The scale is an exact power of two, 2^(s-127). Within one fixed-scale 32-col block, accumulating
unscaled then scaling once is **bit-identical** to per-element scaling, provided every scaled
term/partial stays a finite NORMAL float and term order is unchanged. Scaling by a power of two
commutes exactly with rounding. Equivalence breaks ONLY at subnormal/zero/overflow edges or if the
compiler fuses/reassociates.
=> The "no-FMA scale-per-element form is deliberate for Metal parity" note is over-broad: what
   protects parity is no-FMA + fixed order. The SCALE HOIST itself is likely parity-safe.
   MUST verify empirically with probe_rows16_parity.m, not assumed.

### Numeric edges to guard (Oracle)
|single term| <= 6|act| ; |32-term unscaled block| <= 192|act|max.
s=255 (scale 2^128): single-term overflow near |act| > ~1/6; block overflow near |act| > ~1/192.
s=0   (scale 2^-127): whole block underflows to zero near |act| < ~1.2e-9; subnormals much earlier.
In normal-range blocks deferred-scale error is usually EXACTLY ZERO, not merely small.
Also: coli_e8m0_decode :13503 returns NaN for 0xff. Handle.
Build must disable FP contraction/reassociation where parity matters (-ffp-contract=off).
